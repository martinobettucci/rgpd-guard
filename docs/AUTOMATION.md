# Garde-fous exécutables et orchestration

Ce document est le contrat des garde-fous déterministes et de l'orchestration optionnelle par sous-agents qui appliquent la méthode de `CLAUDE.md`. Les hooks Git sont de fines adaptations au-dessus de scripts versionnés, réutilisables par un humain, un worker planifié et la CI.

Les contrôles propres à un projet ne sont pas décrits ici : ils vivent dans le script `scripts/project-pre-commit` du dépôt et dans sa documentation locale.

<a id="local-guards"></a>
## 1. Principes des garde-fous locaux

- Les hooks contrôlent uniquement ce que Git permet d'établir mécaniquement : identité, destination d'un push, forme de la traçabilité, signatures interdites, erreurs de diff, fichiers d'environnement et secrets évidents.
- Ils n'effectuent jamais de stash, rebase, merge, commit ni push automatique et ne modifient pas l'identité Git.
- Ils ne remplacent ni la revue, ni les preuves fonctionnelles, ni la vérification visuelle. Leur contournement local ne contourne pas les contrôles distants.
- Ils nécessitent Bash, Git et les outils Unix usuels (`grep`, `sed`, `mktemp`, `cp`), sans installation de paquet.
- Le harnais `tests/git-hooks/test-hooks` prouve leur comportement dans des dépôts temporaires qu'il crée et supprime lui-même.

<a id="hook-installation"></a>
## 2. Installation

```bash
scripts/git-hooks/install            # mode standard
scripts/git-hooks/install --worker   # mode worker planifié
```

L'installation exige que `.githooks/pre-commit`, `.githooks/commit-msg` et `.githooks/pre-push` existent et soient exécutables, et refuse d'écraser un `core.hooksPath` différent déjà configuré. Elle pose :
- `core.hooksPath=.githooks` ;
- `factory.hooks.mode` à `standard` ou `worker` ;
- `factory.hooks.baseline` au commit courant lors de la première activation, pour borner les contrôles de push sur un historique antérieur aux hooks.

L'identité Git (`user.name`, `user.email`) reste à poser explicitement dans la configuration locale du dépôt.

<a id="pre-commit-hook"></a>
## 3. Hook pre-commit

`scripts/git-hooks/check-staged` refuse le commit lorsque :
- `git diff --cached --check` signale une erreur d'espaces ;
- l'identité locale est absente, ou l'identité effective de l'auteur ou du committer diffère de l'identité locale (variable d'environnement ou option `--author`) ;
- en mode worker, `HEAD` n'est pas attaché à `main` ;
- un fichier `.env` ou `.env.*` est indexé (seuls `.env.example`, `.env.sample` et `.env.template` sont admis) ;
- une ligne ajoutée contient un secret évident : en-tête de clé privée PEM, identifiant de clé d'accès cloud, jeton de forge ou de messagerie aux préfixes connus ;
- un fichier de code indexé ne porte pas, dans ses 60 premières lignes, un `@spec` vers `docs/BACKLOG.md#identifiant` (ou, en l'absence de backlog, vers un contrat documentaire `chemin.md#ancre`) ;
- un fichier de test indexé ne porte pas, dans ses 60 premières lignes, un `@verifies` de même forme.

Sont des fichiers de code : le contenu de `.githooks/`, les fichiers sans extension de `scripts/` et `tests/`, `Makefile`, `Dockerfile` et leurs variantes, et les extensions de langages, de styles, de gabarits et de configuration (`py`, `sh`, `ts`, `tsx`, `js`, `css`, `html`, `sql`, `toml`, `yaml`, `yml` et équivalents). Les fichiers JSON et Markdown n'en font pas partie.

Sont des fichiers de test : les chemins contenant `test/`, `tests/` ou `__tests__/`, et les noms `test_*`, `*_test.*`, `*.test.*`, `*.spec.*`, `verify-*`.

Lorsque `scripts/project-pre-commit` existe, il doit être exécutable et il est exécuté après ces contrôles ; son échec refuse le commit.

<a id="commit-message-hook"></a>
## 4. Hook commit-msg

`scripts/git-hooks/check-message` refuse un message qui contient une attribution ou une signature interdite : trailer `Co-Authored-By`, mention « generated with » ou « generated by » suivie d'un outil d'IA, mention « AI generated », lien de session d'agent.

<a id="pre-push-hook"></a>
## 5. Hook pre-push

`scripts/git-hooks/check-push` contrôle chaque commit sortant (depuis l'état distant connu, ou depuis la baseline) : auteur et committer identiques à l'identité locale, message sans attribution interdite. En mode worker, il exige en plus `HEAD` sur `main`, le remote `origin`, la destination `refs/heads/main`, l'absence de suppression et un fast-forward.

<a id="subagents"></a>
## 6. Sous-agents

Quatre rôles bornés sont définis pour Claude Code (`.claude/agents/`) et pour Codex (`.codex/agents/`, adaptateur `AGENTS.md`) :

| Rôle | Mission | Écriture |
|---|---|---|
| `factory-explorer` | cartographier contrats, dépendances et flux réels | aucune |
| `factory-reviewer` | relire un changement stabilisé contre ses contrats | aucune |
| `factory-verifier` | exécuter une preuve documentée et analyser ses résultats | artefacts temporaires attendus uniquement |
| `factory-resolver` | instruire une entrée du registre d'incohérences et proposer son issue | aucune |

L'agent principal reste l'unique éditeur des fichiers suivis et l'unique opérateur Git. Chaque délégation nomme objectif, périmètre, sources et livrable ; les sous-agents ne délèguent pas, ne décident pas et ne clôturent rien. Le vérificateur relève `git status` avant et après son exécution et signale tout écart. La délégation est facultative et son indisponibilité ne bloque jamais une unité.

<a id="session-guard"></a>
## 7. Garde de fin de session

`scripts/git-hooks/check-session` est en lecture seule et sert de condition de terminaison au worker planifié. Il exige : `HEAD` attaché à `main`, `core.hooksPath=.githooks`, mode `worker`, aucune opération Git inachevée, un working tree et un index propres, `HEAD` égal à `origin/main`, aucun stash de sauvegarde initiale oublié.
